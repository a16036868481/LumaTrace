Milestone 4B hardens the Tauri packaging foundation. It is not a formal production release.

## Toolchain Detection

`pnpm detect:tauri-toolchain` checks `cargo`, `rustc`, optional `rustup`, Tauri CLI availability, Node, pnpm, platform, and architecture. It does not install Rust or Tauri CLI.

If `cargo` is missing, detection still exits successfully and reports missing tools. `pnpm check:tauri`, `pnpm dev:tauri`, and `pnpm build:tauri` require the Rust/Tauri toolchain and may fail clearly on machines without it.

Milestone 4B-4 must start with `pnpm detect:tauri-toolchain`. If Rust/Cargo or the Tauri CLI are missing, the batch stops at documented missing-tool status. Project scripts must not auto-install Rust or claim Tauri dev/build success without actually running those commands on a machine where the detector reports the required tools.

Current Windows real-machine verification has been run with Rust/Cargo/rustc/rustup, Microsoft C++ Build Tools, WebView2 Runtime, and Tauri CLI available. `pnpm check:tauri` and `pnpm build:tauri` pass. `pnpm dev:tauri` has been smoke-validated by launching the dev app, observing the Tauri runtime start, and confirming the sidecar supervisor records sidecar startup; because it is a long-running development command, automated smoke stops it after startup.

## Windows Optional Tool Bootstrap

`pnpm detect:windows-tools` detects Android SDK Platform-Tools (`adb`) and PresentMon Console. `pnpm bootstrap:windows-tools` can install missing tools through fixed winget package IDs (`Google.PlatformTools` and `Intel.PresentMon.Console`) and configure user-level environment variables for newly launched app processes.

This is the planned Windows installer/first-run setup path so end users do not need to manually configure ADB or PresentMon. It is not arbitrary shell execution: package IDs and commands are fixed by the bootstrap script, and the frontend does not receive permission to run arbitrary commands.

LumaTrace still does not bundle ADB or PresentMon directly in production artifacts until license review, notices, signing, and release approval are complete. The current package must keep `productionReady=false`.

## Sidecar Artifact Status

`pnpm build:sidecar` still produces a development wrapper. `pnpm build:self-contained-sidecar` produces the current self-contained draft by bundling a Node.js runtime with a `pnpm deploy --prod` local-server dependency closure and a fixed target-triple sidecar wrapper.

On Windows, Tauri `externalBin` requires an executable sidecar artifact. Both the dev wrapper and the self-contained draft use a small target-triple `.exe` launcher. In the self-contained draft, that launcher prefers `lumatrace-local-server-runtime/node.exe` and the deployed app directory, then falls back to development paths only for local verification.

The self-contained sidecar pipeline is still a draft. Do not claim production-ready packaging while `productionReady: false`, even when the manifest says `artifactKind: "self-contained"`.

The self-contained build writes `packaging-notices.json` and `THIRD-PARTY-NOTICES.md` beside the sidecar artifact. The sidecar manifest stores their file names, SHA-256 hashes, and `licenseReviewStatus: "draft_requires_review"`. `pnpm verify:windows-license-review-template` writes a sanitized `lumatrace-windows-license-review-template.json` from those notice files. The template keeps reviewer fields empty, records `approved: false`, includes component metadata and counts only, and excludes raw license text, tokens, full local paths, raw logs, and stack traces. These notice files and templates are generated for QA and release review; they are not legal approval and do not change `productionReady`.

When a human reviewer produces `lumatrace-windows-license-review-result.json`, `pnpm verify:windows-license-review-result path/to/result.json` checks that the result matches the template's notice hashes and component list, records reviewer approval, and includes per-component decisions. `pnpm smoke:windows-packaging-rc-gate-license-review-result` verifies that such a result removes only the `LICENSE_NOTICE_REVIEW` blocker. It does not grant release approval, sidecar production readiness, code signing, updater policy, or `productionReady=true`.

## Security Boundaries

- Packaged local-server binds only to `127.0.0.1`.
- Packaged REST and WebSocket require a memory-only bearer token.
- The token is not placed in `VITE_`, localStorage, URLs, logs, reports, or diagnostics.
- No arbitrary shell command permission is granted to the frontend.
- Sidecar restart is limited and diagnostics are sanitized.

## Crash Recovery

Milestone 4B-3 adds an explicit sidecar crash recovery state machine. States include `starting`, `running`, `stopping`, `stopped`, `crashed`, `restart_limited`, `auth_failed`, `port_conflict`, `db_migration_failed`, and `shutdown_requested`.

Normal graceful shutdown is not treated as a crash. Non-zero exits are classified from sanitized stdout/stderr excerpts. The restart cooldown defaults to 5000 ms and the restart limit defaults to 3 attempts. The supervisor must not restart forever, and crash evidence must not include tokens, raw stderr/stdout, full paths, or stack traces.

## Logs And Storage

Packaged mode uses AppLocalData and AppLog. Milestone 4B-3 adds packaged storage status and packaged storage smoke.

Log rotation applies only to AppLog files named `app.log`, `local-server.log`, `sidecar-supervisor.log`, and `packaging-diagnostics.log`. The default policy is 10 MB per file, 5 retained files, rotate on startup, rotate when the threshold is exceeded, and delete the oldest rotated file.

Diagnostics export is sanitized JSON. Raw logs are not exported; only short sanitized excerpts and metadata are included. Auth tokens, full local paths, command lines, raw stdout/stderr, raw PresentMon CSV, logcat, bugreport data, Android full serials, emails, and stack traces are redacted or omitted.

Packaged storage status reports DB existence, DB size, migration status, migration versions, session count, report count, and reports/diagnostics directory availability with sanitized paths. `pnpm smoke:packaged-storage` creates a mock session, generates a report, shuts down local-server, restarts with the same `dbPath`, and verifies the session/report remain readable without duplicate migration failure.

## Not In 4B

No updater, no production code signing, no notarization, no store distribution, no iOS, no cloud, no production installer, no production-ready sidecar, and no new metrics are implemented in this milestone.

`pnpm verify:windows-packaging-release-readiness` is a release gate, not a release approval. It summarizes the sidecar manifest, QA evidence, notice manifest, Windows bundle draft, and installer draft using file names, hashes, sizes, and status booleans only. It deliberately keeps `releaseStatus: "blocked"` and records blockers for code signing, updater policy, release approval, sidecar production readiness, and manual GUI QA when applicable. It must not contain auth tokens, local paths, raw logs, command lines, stack traces, or `productionReady: true`.

`pnpm verify:windows-code-signing-readiness-template` is a signing-readiness checklist, not a signing command. It records relative artifact file names, SHA-256 hashes for existing unsigned artifacts, empty reviewer fields, certificate/timestamp/verification booleans set to false, and explicit security assertions. It must not contain certificate files, private keys, passwords, signtool command lines, full local paths, raw logs, stack traces, tokens, or `productionReady: true`.

When an external signing process produces `lumatrace-windows-code-signing-readiness-result.json`, `pnpm verify:windows-code-signing-readiness-result path/to/result.json` checks that it records sanitized certificate and timestamp summaries, verifies the same artifact list as the template, marks existing RC artifacts as signature-verified, and excludes certificate secrets, signing command lines, full paths, raw logs, tokens, and stack traces. `pnpm smoke:windows-packaging-rc-gate-code-signing-result` verifies that such a result removes only the `CODE_SIGNING` blocker. It does not grant release approval, sidecar production readiness, updater policy, or `productionReady=true`.

`pnpm verify:windows-updater-policy-readiness-template` is an updater-readiness checklist, not an updater implementation. It records relative draft artifact names, hashes for existing manifests, empty reviewer fields, updater/update-signing/rollback/verification booleans set to false, and explicit security assertions. It must not contain endpoint secrets, private keys, passwords, update signing command lines, full local paths, raw logs, stack traces, tokens, or `productionReady: true`.

When an external policy review produces `lumatrace-windows-updater-policy-readiness-result.json`, `pnpm verify:windows-updater-policy-readiness-result path/to/result.json` checks only the sanitized strategy decision. The 4B-compatible result keeps `autoUpdateEnabled=false`, excludes updater endpoints with secrets, update signing commands, keys, full paths, raw logs, tokens, and stack traces, and can remove only the `UPDATER_POLICY` blocker. It does not enable an updater, publish update metadata, approve a release, grant sidecar production readiness, or change `productionReady=false`.

`pnpm verify:windows-release-approval-readiness-template` is a release-approval readiness checklist, not release approval. It records relative evidence file names, hashes for existing evidence, empty reviewer fields, approval booleans set to false, required-evidence booleans, and explicit security assertions. When an external release reviewer produces `lumatrace-windows-release-approval-readiness-result.json`, `pnpm verify:windows-release-approval-readiness-result path/to/result.json` checks the sanitized approval summary against the template evidence. `pnpm smoke:windows-packaging-rc-gate-release-approval-result` verifies that such a result removes only the `RELEASE_APPROVAL` blocker. `pnpm verify:windows-sidecar-production-readiness-template` is a sidecar-readiness checklist, not approval. It deliberately excludes raw third-party license text, reviewer notes, evidence notes, raw logs, command lines, raw CSV, logcat, bugreport data, tokens, Android full serials, and full local paths. It is not release approval and it must keep `rcCandidateReady=false` plus `productionReady=false`.

The Windows bundle draft remains a portable release-directory check. It does not produce MSI, NSIS, MSIX, or any signed installer artifact. The separate Windows installer draft probe may produce an unsigned NSIS setup artifact for QA only; its manifest must keep `unsigned: true`, `productionReady: false`, `codeSigningConfigured: false`, and `updaterConfigured: false`. The installer smoke installs only into a temporary directory, verifies expected resources, runs the uninstaller, and removes the temp directory. The Tauri sidecar auth transport smoke records a sanitized manifest proving the dev app observed a sidecar process without auth material in launch arguments and with localhost binding only. The installed app launch smoke uses the same temporary install boundary, starts the installed app executable, records only sanitized startup metadata, and still does not claim full interactive GUI QA or production readiness. The installed sidecar health smoke adds an observable local networking check and fails if the sidecar exposes a non-loopback listener. The packaging smoke suite verifier aggregates the resulting manifests, checks that each remains sanitized and non-production-ready, and writes `lumatrace-windows-packaging-smoke-suite-manifest.json`. The QA evidence exporter then writes `lumatrace-windows-packaging-qa-evidence.json`, which is useful for audit trails and records manual GUI QA as `not_run` until a validated result file is present. The manual GUI QA template exporter writes `lumatrace-windows-manual-gui-qa-template.json`, with reviewer fields empty and every checklist item set to `pending`, so it cannot be mistaken for a completed review. `pnpm verify:windows-manual-gui-qa-handoff` writes a sanitized `lumatrace-windows-manual-gui-qa-handoff/` directory and manifest for the reviewer; it includes the checklist, pending template, automated evidence, RC gate, release policy template, sidecar manifest, and notice drafts, but deliberately excludes a completed manual result and all raw logs. After a reviewer fills a result JSON, `pnpm verify:windows-manual-gui-qa-result path/to/result.json` checks every item has a final status and required notes, rejects token/path/raw-log/stack evidence, and still requires `productionReady=false`. If `lumatrace-windows-manual-gui-qa-result.json` is present beside the other release manifests, the QA evidence exporter includes only a sanitized manual result summary: status, hash, size, reviewer presence booleans, and step counts. It never copies reviewer notes or evidence notes into the aggregate evidence. Manual GUI QA remains a separate checklist because it requires human inspection of the installed app window and workflows.

The Windows preview release command is a GitHub prerelease publisher, not production approval. `pnpm release:windows-preview -- --tag v0.1.0-preview.N --publish` requires an explicit tag and GitHub CLI authentication, keeps the installer unsigned, and keeps `productionReady=false`. Use `--dry-run` to stage the same assets without creating a tag or release.

`/api/packaged/status` and `/api/packaged/diagnostics/export?format=json` also expose the manual GUI QA handoff summary when `lumatrace-windows-manual-gui-qa-handoff-manifest.json` is present. The summary intentionally keeps `manualGuiQaStatus: "not_run"` and `productionReady=false`; it does not copy reviewer results, reviewer notes, raw logs, tokens, command lines, stack traces, or full local paths.
